# Data Models Reference

This page documents the core data structures used across DecisionBox.

## DiscoveryResult

A complete discovery run output. Stored in the `discoveries` MongoDB collection.

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | MongoDB ObjectID |
| `project_id` | string | Project that owns this discovery |
| `run_id` | string | The run that produced this result. Lets a resumed run retire the partial result its previous attempt left behind, and keep that result out of its own "previously discovered" context. Absent on documents written before resume shipped, which every reader treats as "not this run". |
| `domain` | string | Domain (e.g., `gaming`, `social`) |
| `category` | string | Category (e.g., `match3`, `idle`, `casual`, `content_sharing`) |
| `run_type` | string | `full` (all areas), `partial` (some areas or some failed), `failed` (all areas failed) |
| `areas_requested` | string[] | Area IDs requested (empty for full run) |
| `discovery_date` | timestamp | When the discovery ran |
| `total_steps` | int | Number of exploration steps executed |
| `duration` | int64 | Duration in nanoseconds |
| `insights` | Insight[] | Discovered patterns |
| `recommendations` | Recommendation[] | Actionable advice |
| `summary` | Summary | Aggregate stats |
| `created_at` | timestamp | When result was saved |
| `updated_at` | timestamp | Last write timestamp |

Discovery logs are stored in split collections rather than embedded on the document: `discovery_exploration_steps`, `discovery_analysis_steps`, `discovery_validation_results`, and `discovery_recommendation_log`. See [Discovery log collections](../architecture/discovery-log-collections.md) for the rationale and the document shapes.

## Insight

A discovered pattern or finding. Generated by the analysis phase.

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Deterministic ID: `{area}-{index}` (e.g., `churn-1`, `monetization-3`). Auto-generated if LLM omits it. |
| `analysis_area` | string | Which area found this (e.g., `churn`, `levels`) |
| `name` | string | Specific descriptive name (e.g., "Day 0-to-Day 1 Drop: 67% Never Return") |
| `description` | string | Plain-text description with exact numbers and percentages. The raw, formatting-free form read by API consumers, list/preview UIs, and embeddings |
| `description_md` | string | GitHub-Flavored Markdown rendition of `description` (emphasis, lists, small sub-headings, simple tables), rendered formatted on the insight detail view. Omitted on unformatted and pre-Markdown (legacy) insights — the dashboard falls back to `description` |
| `severity` | string | `high`, `medium` or `low`, **derived** from the figures the platform re-checked — not written by the analysis model. The band behind `scoring.severity_band`; kept as its own field because it is a live vector-search filter and sits inside the dedup embedding text. A document written before severity was derived may carry `critical`, which is now the top **priority tier** rather than a severity |
| `affected_count` | int | Number of affected users (COUNT DISTINCT user_id). Deliberately **not** an input to severity: it is a model-authored integer with no population denominator anywhere in a run to turn it into a share |
| `risk_score` | float64 | 0.0 to 1.0, **derived** — the continuous score behind `severity`, clamped so the readers that print it as a percentage keep working |
| `confidence` | float64 | 0.0 to 1.0, **derived** from the validation verdict and the evidence trail — not written by the analysis model. The continuous score behind `scoring.confidence_band`; kept as its own field because it is what the lists sort on |
| `scoring` | Scoring | The derived grade and the arithmetic behind it. Absent on documents written before the scorer shipped, which the dashboard renders as legacy |
| `metrics` | map | Flexible key-value metrics (e.g., `{"churn_rate": 0.67, "avg_sessions": 3.2}`) |
| `indicators` | string[] | Specific metric indicators (e.g., "Session drop: 12min → 4min") |
| `target_segment` | string | Description of affected user segment |
| `source_steps` | int[] | Exploration step numbers that support this insight |
| `validation` | InsightValidation | Warehouse verification result (if validated) |
| `discovered_at` | timestamp | When this insight was generated |

### Scoring

The derived grade, attached to an insight or a recommendation by the scorer.

`confidence` is a function of the validation verdict, docked for the evidence the run checked and found wanting.
`severity` is a function of the figures the platform re-evaluated against warehouse rows, multiplied by the analysis area's weight.
`priority` is a rollup of the two.
The analysis model is not asked for any of them: a model grading its own work produced a confidence that spanned 0.75 to 0.99 with a mean of 0.93 over 160 stored insights, while nine of those had been contradicted by the warehouse and forty-three carried arithmetic the platform refuted and could not repair — and `severity` was the same self-assessment in words, so a finding whose headline number the warehouse had refuted could still call itself critical.
The scorer clears every one of these fields and writes them from the evidence, which is why removing the ask from the prompts was not sufficient on its own — a project snapshots its area prompts at creation and a pack's seeds are never overwritten on upgrade, so an existing deployment keeps asking the model for them indefinitely.

| Field | Type | Description |
|-------|------|-------------|
| `confidence_band` | string | `high`, `medium`, `low`, `not_confirmed` or `unverifiable`. The first three come from where the score falls; the last two come from the verdict and are terminal, because "nothing could check this" and "this was never checked" are different statements from "checked and weak" |
| `confidence_base` | float64 | What the verdict alone was worth, before any deduction |
| `confidence_score` | float64 | The score after every deduction, floored. The same number as the document's own `confidence` |
| `confidence_reason` | string | The engine's own words for why the score is what it is. Stored on the document so every reader quotes one wording |
| `confidence_docks` | ConfidenceDock[] | Each deduction that was charged, in order |
| `engine_version` | int | Which calibration produced these numbers. [`GET /api/v1/scoring/engines`](api.md#scoring) serves the cutoffs per version, so a document explains itself with the ones that actually scored it |

| `magnitude_score` | float64 | The **weight-free** magnitude: what the checked figures say about size, before any business weight. Kept beside `severity_score` because it is what a comparison across runs has to use — the severity word changed vocabulary when severity stopped being the model's, and a weighted score moves when an area's weight does, so neither answers "did this finding actually grow" |
| `severity_band` | string | `high`, `medium` or `low`. Absent on a document an earlier engine version scored on the confidence axis alone, which is how a reader tells "never graded" from "graded low" |
| `severity_score` | float64 | `min(1.0, magnitude × area_weight)`. The same number as the document's own `risk_score` |
| `severity_driver` | SeverityDriver | The figure the magnitude came from, and the amount the finding is about |
| `severity_reason` | string | The engine's own words for the band, stored so every reader quotes one wording |
| `area_weight` | float64 | The multiplier applied to the magnitude: the analysis area's per-area override, else the largest weight among its risk categories, else `1.0`. See [Risk taxonomy and severity weights](#risk-taxonomy-and-severity-weights) |
| `weight_source` | object | `kind` is `default`, `category` or `area_override`, with `category` naming the one that set it. Written even when the default applied, so a reader can tell a deliberate `1.0` from an unwritten field |
| `priority_tier` | string | `critical`, `investigate`, `high` or `low` — the matrix cell over the severity and confidence bands. Absent together with the severity half, because there is nothing to roll up without it |
| `priority_score` | float64 | The sort key: the tier's weight plus a small refinement from the two continuous scores. Monotone in the tier, so no amount of severity or confidence lifts a finding over the tier above it |
| `risk_flags` | string[] | What **kind** of risk this finding is: the risk category ids its analysis area maps to, in the area's own declaration order. Derived from the area — the analysis model cannot author one. Absent on a document whose area maps to no category |

#### SeverityDriver

What a reader is shown beside a severity band, rather than the band on its own.

| Field | Type | Description |
|-------|------|-------------|
| `kind` | string | What banded the magnitude: `amount`, `share` or `baseline` |
| `quantified` | bool | False only for `baseline` — no checked figure could be found, so the magnitude is the area baseline and the label reads *not quantified*. This is **not** a low magnitude: an unquantified finding is unmeasured, not small |
| `figure` | SeverityFigure | The figure the magnitude was banded from. Absent for `baseline` |
| `amount` | SeverityFigure | The largest checked amount the document states in its own home currency, when it states one — the money at stake. Present whether or not it banded anything |

A `SeverityFigure` carries `figure_id`, `display` (the figure as the prose renders it), `value`, `unit`, `currency` and `verdict` — the platform's own conclusion about that figure's arithmetic, always `holds` on a figure the engine would use.

**Two figure slots, and both are load-bearing.** An absolute money cutoff is a property of a business rather than of the engine, so `amount_bands` ships empty (see [`GET /api/v1/scoring/engines`](api.md#scoring)) and an unconfigured deployment cannot band an amount at all. What it can still do is extract the amount and show it, while the band comes from the share — which is the usual case, not an edge one, and is why `figure` and `amount` are usually two different figures. They name the same figure once amount bands are configured.

**Magnitude comes only from figures the platform re-checked**, in this order: the largest currency figure whose verdict holds and whose currency is the document's home currency (banded by the configured amount bands), then the largest percentage figure whose verdict holds, then the area baseline. Largest by *absolute* value — a 12% fall matters as much as a 12% rise. A figure the warehouse refuted, one the evaluator could not settle, and one with no verdict at all are the same thing here: a number that was not checked.

#### Risk taxonomy and severity weights

Not every analysis area matters equally. A domain pack declares a **risk taxonomy** — the business-risk categories its domain has, with a weight each — and maps every analysis area to one or more of them. A project overrides any category's weight deployment-wide, and a single area can override the weight its categories would give it.

```
weight(area) = the area's own severity_weight, when one is configured
             | max(weight(c) for c in the area's risk_categories)
             | 1.0                                                     (the engine default)
risk_flags   = the area's risk_categories, deduped, in declaration order
```

**`max`, not the product or the mean.** A product double-counts: a finding that is both a revenue leak (2.0) and a compliance exposure (3.0) would be weighted 6.0 and clamp to the top of the scale whatever its magnitude. A mean dilutes the category that matters by averaging it with one that does not. `max` says *weighted by whichever is worse*, which is the sentence a reader expects from a list ordered by it.

**Multipliers, not band floors.** "Compliance is always at least high" collapses everything it touches onto one band and sorts nothing; the continuous score is what orders twenty findings *inside* a band. A weight of 3.0 lifts a low-magnitude finding (0.25) above the high cutoff (0.66) without flattening anything: 0.25 × 3.0 = 0.75 outranks a medium-magnitude finding in an unweighted area (0.60 × 1.0).

A stated weight must be in **(0, 3]**. Zero is excluded because it multiplies a magnitude to nothing and removes every finding in the category from the ranking, silently and in the direction that hides findings; the ceiling is what keeps a weight a weight, since the score is clamped at 1.00 and an unbounded one would produce a column of identical values. [`GET /api/v1/scoring/engines`](api.md#scoring) serves the ceiling and the cross-cutting category ids, so no client restates them.

**Three category ids are the engine's own** and are available to every pack, whether or not it declares a taxonomy: `compliance`, `security` and `data_quality`. They flag a finding without weighting it unless a pack or a project declares a weight for them.

| Where | Field | Scope |
|---|---|---|
| Domain pack | `risk_taxonomy` (`id`, `label`, `description`, `weight`) | The pack, and so the warehouse it is bound to |
| Domain pack / project area | `risk_categories`, `severity_weight` | The pack, and so the warehouse — a project snapshots both at creation and they are editable per area on the playbook page |
| Project | `category_weights` | The project, across every datasource: "compliance is three times anything else for us" is not a per-warehouse statement |
| Discovery run | `scoring_config` | One run, pinned at its first attempt |

**A run's weighting is pinned.** `scoring_config` records the resolved category weights and each configured area's mapping at the run's first attempt, and every later attempt replays it. A resume can happen days after the attempt it continues, and a weight changed in between would score the second half of a run against different numbers from the first. It stores the resolved *inputs* rather than the per-area weights, so a later attempt re-derives both the weight and the flags through the same engine code the first used.

**A weight change is not a trend.** The cross-run comparison in the discovery ledger reads `magnitude_score`, which is weight-free, precisely so that raising a category's weight cannot make every finding in it look as though it got worse on the day someone changed a setting.

**Nothing is re-scored.** A stored `severity` is an immutable fact about the run that produced it: changing a weight changes what the next run computes and leaves every stored document alone, and the on-demand "Run validation" path re-derives the confidence axis only.

#### Priority

The matrix, over the severity band and whether the confidence band is trusted (`high` or `medium`) or not (`low`, `unverifiable`, `not_confirmed`):

| severity ↓ / confidence → | trusted | untrusted |
|---|---|---|
| **high** | `critical` | `investigate` |
| **medium** | `high` | `low` |
| **low** | `low` | `low` |

`investigate` outranks the `high` tier deliberately: a severe finding nothing could check is the one a reader most needs to see, because severity sets the ceiling and confidence only refines inside it.

No derivation is stored for priority — the cell is recomputable from the two bands, which is what a reader is shown. The per-run tier tally is computed where the list renders rather than persisted, so it cannot go stale when a document is re-validated.

#### ConfidenceDock

| Field | Type | Description |
|-------|------|-------------|
| `code` | string | `degraded_evidence`, `refuted_arithmetic`, `refuted_quantifier`, `unresolved_figure` or `sample_ended_early` |
| `label` | string | The engine's own words for the signal, rendered verbatim by the dashboard |
| `amount` | float64 | The magnitude charged, always positive |

The amounts always sum to exactly `confidence_base − confidence_score`.
A deduction a cap or the floor reduced is stored reduced, and one reduced to nothing is not stored at all — so the breakdown a reader opens adds up, rather than leaving them to infer that a cap applied somewhere.

The verdict bases, the band cutoffs and the deduction amounts are engine constants rather than deployment settings, because a document has to be explainable with the calibration that scored it and an overridable cutoff would make the stored `engine_version` a lie.
A re-calibration is a version bump.

That rule starts at the first deployment whose stored documents we undertake to explain.
Until then the current version is still being calibrated: numbers move, axes are added, and the version does not change — so the completed feature ships as version 1 rather than as whichever number the development sequence happened to reach.
What makes that safe is the degradation contract above: everything a reader needs about a document is stored on the document, the calibration supplies only the line naming the cutoff a score crossed, and a client that cannot find its version — or finds one without the axis it was looking for — omits that line rather than failing.
A document scored by a pre-release calibration is explained by re-running its discovery, not by freezing a version for it.
From the first such deployment onward, a change to any number here is a new version with a new entry, and the old entry is immutable.

### InsightValidation

Attached to an insight after validation by the verifier + refuter pair.

| Field | Type | Description |
|-------|------|-------------|
| `verifier` | StructuredVerdict | Defender-frame agent verdict with per-claim evidence rows |
| `refuter` | StructuredVerdict | Skeptic-frame agent verdict (omitted when refuter is disabled or the refuter run failed) |
| `combined` | string | Combined verdict: `confirmed`, `supported`, `rejected`, `partial`, `unverifiable`, `validation_disabled`, or `skipped_budget_cap` |
| `refuter_disabled` | bool | True when the refuter was intentionally skipped for this document |
| `validated_at` | timestamp | When validation was performed |
| `input_tokens` | int | LLM input tokens consumed during validation |
| `output_tokens` | int | LLM output tokens produced during validation |

Legacy fields (`status`, `original_count`, `verified_count`, `query`, `reasoning`) remain populated on documents written before the verifier+refuter pipeline shipped; the dashboard renders the new fields when present and falls back to the legacy fields otherwise.

## Recommendation

An actionable suggestion based on discovered insights.

| Field | Type | Description |
|-------|------|-------------|
| `id` | string | Recommendation ID |
| `category` | string | Category: `churn`, `engagement`, `monetization`, `difficulty` |
| `title` | string | Specific action title |
| `description` | string | Plain-text explanation with numbers. The raw form read by API consumers and previews |
| `description_md` | string | GitHub-Flavored Markdown rendition of `description`, rendered formatted on the recommendation detail view. Omitted on unformatted and legacy recommendations |
| `priority` | int | 1 (critical) to 5 (optional). P1 = highest priority. |
| `target_segment` | string | Exact segment criteria |
| `segment_size` | int | Number of users in the segment |
| `expected_impact` | Impact | Expected improvement |
| `actions` | string[] | Numbered implementation steps |
| `related_insight_ids` | string[] | UUIDs of insights this recommendation addresses, verbatim from the same discovery's `insights[].id` (e.g., `["6e9261f5-c4ec-404b-bdf0-760a4644f384"]`). Recommendations whose `related_insight_ids` cannot be resolved to an eligible insight are dropped server-side before persistence; see the [`RecommendationStep`](#recommendationstep) `recommendations_dropped*` counters |
| `confidence` | float64 | 0.0 to 1.0, **derived** from this recommendation's OWN validation verdict — not inherited from the insights it cites, and not written by the model |
| `severity` | string | **Inherited** from the insights this recommendation cites: the highest of them. Not measured from its own figures, which are restatements of theirs — measuring them would band a magnitude off numbers already banded once and report the result as independent evidence |
| `priority` | int | 1 (highest) to 5 (lowest), **derived** from `scoring.priority_tier`: `critical` → 1, `investigate` → 2, `high` → 3, `low` → 4. Repopulated rather than repurposed, so the tier order is preserved inside the scale the field has always been documented as; `5` is left unused, and `0` means nothing could be inherited |
| `scoring` | Scoring | The derived grade. Two of the five confidence deductions never fire here: a recommendation is shown insights rather than warehouse rows, so it carries no source-quality caveats and declares no quantifier claims. Its severity half is the inherited one, so its driver is the cited insight's |

### Impact

Expected impact of a recommendation.

| Field | Type | Description |
|-------|------|-------------|
| `metric` | string | What metric improves (e.g., `retention_rate`, `revenue`) |
| `estimated_improvement` | string | Expected improvement (e.g., "+15-20%", "+$4,975/month") |
| `reasoning` | string | Why this improvement is expected |

If an LLM emits `expected_impact` as a bare prose string instead of the object (a common, model-independent behaviour), the agent coerces it into `Impact{reasoning: <string>}` at parse time rather than discarding the recommendation. The same tolerance applies to `segment_size`, which accepts numeric strings.
`confidence`, `severity`, `risk_score` and `priority` are not among them, because none of them is read from model output at all: each key is ignored by the decoder, so a model that volunteers one cannot fail the document and cannot author its own grade. The coercion that used to read descriptive priority words (`"high"`, `"critical"`, `"P2"`) went with the ask — keeping a parser for a field nothing reads would be keeping the shape of the old contract after the contract changed. Providers that support schema-constrained output are additionally asked to emit the object shape at generation time.

## ExplorationStep

One step in the autonomous exploration phase. Drives one user-visible
exploration turn — usually one LLM call, but a turn whose response can't
be parsed is retried (up to a small retry budget) and every retry's
token usage is summed onto the same step.

| Field | Type | Description |
|-------|------|-------------|
| `step` | int | Step number (1-based) |
| `timestamp` | timestamp | When this step ran |
| `action` | string | One of `query_data`, `lookup_schema`, `search_tables`, `complete`, `complete_rejected` |
| `thinking` | string | AI's reasoning for this query |
| `query_purpose` | string | Short description of query intent |
| `query` | string | The SQL statement the model **proposed**. Not necessarily the one that produced `query_result` — see `query_executed`. |
| `query_executed` | string | The statement that actually ran, present only when the self-healing fixer rewrote the proposal. Omitted when the proposal ran unchanged. Read through it rather than choosing between the two fields: a repair can change what the answer means (an observed run had `APPROX_QUANTILES(x,4)[OFFSET(2)]` rewritten to `PERCENTILE_CONT(0.5) WITHIN GROUP`, an approximate median for an exact one). Both are kept because they answer different questions — the proposal is the training signal, the executed statement is the only one that explains the rows. |
| `row_count` | int | Number of rows returned |
| `execution_time_ms` | int64 | Query execution time in milliseconds |
| `error` | string | Error message if query failed |
| `fix_attempts` | int | Number of **applied** LLM repairs for this step's query (0 if it ran cleanly on the first try or if every fix call failed). `fix_attempts <= len(fix_history)`. |
| `fixed` | bool | True if the query was auto-fixed after a SQL error |
| `fix_history` | FixAttempt[] | Per-attempt fix log; omitted (or empty) when no fix was needed. Includes failed attempts (LLM error, unparseable response, filter rejection) — those carry `fixer_error` set. See [FixAttempt](#fixattempt). |
| `tokens_in` | int | Input tokens consumed (sum across any parse-retry rounds on this step) |
| `tokens_out` | int | Output tokens generated (sum across any parse-retry rounds on this step) |

## FixAttempt

One entry per LLM call the self-healing SQL fix loop made for a single
exploration step. Stored as elements of `ExplorationStep.fix_history` in
chronological order. Every entry — including failed attempts whose
proposed SQL was never applied — is recorded so downstream tooling has
visibility into the full repair trajectory, not just the last call.

| Field | Type | Description |
|-------|------|-------------|
| `step` | int | The parent `ExplorationStep.step` number, duplicated for self-contained export. |
| `attempt` | int | Zero-based retry index inside the step. Matches the `attempt` argument the executor passes to the SQL fixer. |
| `prompt_in` | string | Fully rendered prompt the fixer sent to the LLM (system instruction + user message). |
| `response_out` | string | Raw LLM response text — before SQL extraction. Populated even when extraction failed. |
| `sql_before` | string | The broken SQL handed to the fixer. |
| `sql_after` | string | The SQL the fixer proposed. Empty when the fixer failed to extract any parseable SQL (in that case `fixer_error` is set). |
| `error_in` | string | The warehouse error message that triggered this fix call. |
| `fixer_error` | string | When non-empty, the reason the proposal was NOT applied: LLM transport error, unparseable response, or post-fix security-filter rejection. When empty, the proposal was applied and the warehouse was retried with `sql_after`. |
| `input_tokens` | int | Input tokens consumed by this fix call. |
| `output_tokens` | int | Output tokens generated by this fix call. |
| `duration_ms` | int64 | LLM call duration in milliseconds. |
| `timestamp` | timestamp | When this fix attempt was recorded. |

The parent `ExplorationStep.fix_attempts` counter is the number of **applied** repairs (`fixer_error` empty), so `fix_attempts <= len(fix_history)` with the gap being failed-fixer rows.

## RecommendationStep

Full LLM dialog for the recommendation-generation phase, stored in the
`discovery_recommendation_log` collection. One row per discovery run.

| Field | Type | Description |
|-------|------|-------------|
| `run_at` | timestamp | When the recommendation phase ran |
| `prompt` | string | Fully rendered recommendation prompt sent to the LLM |
| `insight_count` | int | Number of eligible insights handed to the recommender |
| `response` | string | Raw LLM response text — before JSON cleanup |
| `tokens_in` | int | Input tokens consumed by the LLM call |
| `tokens_out` | int | Output tokens generated by the LLM call |
| `duration_ms` | int64 | LLM call duration in milliseconds |
| `recommendations` | Recommendation[] | The parsed recommendations actually persisted to the discovery (after the `related_insight_ids` validity check below has dropped any unresolvable ones) |
| `status` | string | Optional observability marker. Empty on the happy path; set to `skipped_no_eligible_insights` when every upstream insight was rejected by the validator so the recommender was never invoked, to `recommendation_parse_error` when the phase produced zero recommendations because the LLM response could not be parsed, or to `recommendation_figures_unresolved` when every recommendation was dropped because its prose referenced figures the model never declared. The dashboard renders the reason for an empty recommendations section. |
| `recommendations_dropped` | int | Number of recommendations the orchestrator discarded before persistence — the sum of the reason-specific counters below (`recommendations_dropped_parse` + `recommendations_dropped_missing_ids` + `recommendations_dropped_unknown_id` + `recommendations_dropped_unresolved_figures`). Omitted on a clean run. |
| `recommendations_dropped_parse` | int | Subset of `recommendations_dropped` skipped because their individual JSON object could not be decoded (e.g. a field with the wrong type). Recommendations are decoded per item, so one malformed entry is dropped and counted here rather than discarding the whole batch. Omitted on a clean run. |
| `recommendations_dropped_missing_ids` | int | Subset of `recommendations_dropped` that arrived with an empty or absent `related_insight_ids` array. Omitted on a clean run. |
| `recommendations_dropped_unknown_id` | int | Subset of `recommendations_dropped` that cited at least one id not present in the eligible insight set — typically slug-style identifiers (`category:severity:theme`) hallucinated by the LLM in place of a real UUID. Use this counter to measure regression rates per LLM provider. Omitted on a clean run. |
| `recommendations_dropped_unresolved_figures` | int | Subset of `recommendations_dropped` whose prose still carried a figure reference after the render pass — a number the model promised and never declared in its `figures` array, so nothing could write a checked value into the sentence. Publishing one would show a literal `{{f1}}` where the amount belongs. Omitted on a clean run. |
| `recommendation_parse_retries` | int | Number of corrective re-prompts the phase issued after a response yielded zero parseable recommendations (bounded by `RECOMMENDATION_PARSE_MAX_RETRIES`). Omitted when zero. |
| `error` | string | Error message if recommendation generation failed (LLM transport error or unparseable response) |

## ValidationResult

Warehouse verification of an insight's claims.

| Field | Type | Description |
|-------|------|-------------|
| `insight_id` | string | ID of the validated insight |
| `analysis_area` | string | Area this insight belongs to |
| `claimed_count` | int | Count claimed by the AI |
| `verified_count` | int | Count verified from the warehouse |
| `status` | string | `confirmed`, `adjusted`, `rejected`, `error` |
| `reasoning` | string | Explanation of the result |
| `query` | string | The verification SQL query |

| `output_tokens` | int | Output tokens summed across the same set. Omitted on legacy rows. |

| `phase` | string | Current phase: `init`, `schema_discovery`, `exploration`, `analysis`, `validation`, `recommendations`, `saving`, `complete` |

| `pause_deadline_at` | timestamp | When an unhonoured pause request lapses (`DISCOVERY_PAUSE_DRAIN_TIMEOUT` past the request). Past it the agent ignores the request. Absent when the deadline is disabled. |

## ExplorationCheckpoint

One exploration step of an **in-flight** run. Stored in the `discovery_checkpoints` collection, keyed by `run_id`, and the reason a crashed run can be resumed instead of paying for its whole exploration phase again.

One document per step rather than an array on the run document, for the same reason the discovery logs were split out: an embedded array grows with run length and a long run hits the 16MB BSON limit exactly when the checkpoint matters most.

Not the same thing as `discovery_exploration_steps`, which is the tail-written audit log keyed by `discovery_id`, carries full rows and fix history, and is read by the dashboard. These rows exist only while a run is in flight, carry a bounded row sample, and are deleted when the run completes or is cancelled — with `DISCOVERY_CHECKPOINT_RETENTION` as the backstop.

| Field | Type | Description |
|-------|------|-------------|
| `run_id` | string | The run this checkpoint belongs to |
| `project_id` | string | Project that owns the run |
| `step_number` | int | 1-based step number; `0` is the reserved exploration-summary document |
| `attempt` | int | Which attempt wrote this row (observability — a mixed set across a prefix is how an operator sees where the previous attempt stopped) |
| `kind` | string | `step` or `exploration_summary` |
| `created_at` | timestamp | TTL anchor |
| *(inline)* | ExplorationStep | The step itself, with its result set reduced to a bounded row sample and its fix history and raw LLM dialog stripped |
| `datasource_id` | string | Replay argument: the datasource the action targeted |
| `lookup_schema` | string[] | Replay argument for a `lookup_schema` step |
| `search_tables`, `search_top_k` | string, int | Replay arguments for a `search_tables` step |
| `correlation_a`, `correlation_b` | string | Replay arguments for a `get_correlations` step |
| `reject_reason` | string | Reason class behind a `complete_rejected` step, so the nudge can be re-derived |
| `completed`, `completion_msg`, `total_steps`, `exploration_duration_ms` | — | Summary document only (`kind` = `exploration_summary`). Its presence is what lets a resumed run skip exploration entirely. |

The summary document's `attempt` carries a second meaning: it identifies the exploration a resumed run is about to work over, and it is the value every `AnalysisAreaCheckpoint` is stamped with and filtered on.

Indexes: `(run_id, step_number)` unique — which makes a retried write a replace rather than a duplicate — and a `created_at` TTL named `ttl_discovery_checkpoint`.

The replay arguments are stored separately because an `ExplorationStep` records what came BACK (rows, counts, errors, digest) but has no field for what was ASKED — there is nowhere on it to put a lookup's table refs or a search's query text, and replay has to rebuild the model's own prior turn.

See [Discovery lifecycle](../concepts/discovery-lifecycle.md#checkpointing-and-resume) for what a checkpoint deliberately does not keep, and why.

## AnalysisAreaCheckpoint

One **completed** analysis area of an in-flight run. Stored in the `discovery_analysis_checkpoints` collection, keyed by `(run_id, area_id)`, and the reason a resumed run analyses only the areas its previous attempt had not finished.

A sibling collection rather than another `kind` inside `discovery_checkpoints`: that collection's unique index is `(run_id, step_number)` and an area has no step number, and both of its readers scan a run's rows in step order and stop the replayable prefix at the first unexpected number.

Not the same thing as `discovery_analysis_steps`, which is the tail-written audit log keyed by `discovery_id` and read by the dashboard. These rows exist only while a run is in flight and are deleted when the run completes or is cancelled — with `DISCOVERY_CHECKPOINT_RETENTION`, the same setting that governs the exploration checkpoints, as the backstop.

| Field | Type | Description |
|-------|------|-------------|
| `run_id` | string | The run this checkpoint belongs to |
| `project_id` | string | Project that owns the run |
| `attempt` | int | Which attempt analysed this area. The upsert is fenced on it, so an orphaned earlier attempt cannot overwrite a newer one's area |
| `exploration_attempt` | int | The attempt that wrote the exploration summary this area was analysed over. A resumed run restores only the rows matching the exploration it is itself working over — an area's insights cite exploration step numbers, so one analysed over a *different* exploration would attribute its evidence to the wrong queries |
| `insights_validated` | int | How many of the area's insights were submitted to the verifier, so a resumed run restores the per-run validation budget instead of handing the areas it still has to run a fresh one |
| `created_at` | timestamp | TTL anchor |
| *(inline)* | AnalysisStep | The area itself — prompt, response, token counts, picker telemetry, its insights with their validation verdicts and evidence-quality labels, and its validation results. Nothing is stripped: an area's size is already bounded by the picker's token budget, and this is the same payload Phase 7 writes to `discovery_analysis_steps` |

The stored insight ids are the ones the attempt that produced the area assigned, and a resumed run does **not** reuse them: it mints fresh ids as it merges the area back in, and re-points the area's validation results at them. An insight id keys the embedded insight, the standalone row and the Qdrant point, so an id carried across attempts would collide with what the previous attempt had already written — see [Discovery lifecycle](../concepts/discovery-lifecycle.md#phase-7-save) for the three failures that follow.

Indexes: `(run_id, area_id)` unique — which makes re-analysing an area a replace rather than a duplicate — and a `created_at` TTL named `ttl_discovery_analysis_checkpoint`.

The inlined `AnalysisStep` supplies `area_id`, so there is no separate field for it; the key half of the unique index comes from the step itself.

A row exists only for an area that produced a parsed result, finished its validation and had its evidence-quality labels attached. An area whose analysis failed carries no row, so a resume retries it — see [Discovery lifecycle](../concepts/discovery-lifecycle.md#what-a-completed-analysis-area-keeps) for why that distinction is what makes a deadline-killed run recoverable.

## AnalysisAreaDraft

One analysis area of an in-flight run that has been **analysed but has not finished validating its insights**. Stored in the `discovery_analysis_drafts` collection, keyed by `(run_id, area_id)`, and the reason a resumed run finishes such an area rather than re-analysing it.

A separate collection from `discovery_analysis_checkpoints` rather than a flag on the same row, because the two are read differently: a completed area is restored and *skipped*, a draft is restored and *finished*. A reader that could not tell them apart would admit insights carrying no validation verdict into the run's result, and a flag on a shared row is honoured only by readers that know about it — so an older agent resuming the same run would apply the older meaning to it.

| Field | Type | Description |
|-------|------|-------------|
| `run_id` | string | The run this draft belongs to |
| `project_id` | string | Project that owns the run |
| `attempt` | int | Which attempt analysed this area. The upsert is fenced on it, so an orphaned earlier attempt cannot overwrite a newer one's draft |
| `exploration_attempt` | int | The attempt that wrote the exploration summary this area was analysed over. The same staleness fence the completed-area rows carry, for the same reason: the insights cite exploration step numbers |
| `insight_verdicts` | object | One validation verdict per insight already submitted to the verifier, keyed by the insight id as this document holds it. Written one field at a time rather than by re-writing the row, because the verdicts are produced concurrently and two document replaces would lose one of them |
| `missing_value_figures` | object | Per insight id, which of its figures the model declared no readable value for — `Figure.ValueMissing` is `bson:"-"`, and a restored figure without the flag reads as a real zero |
| `created_at` | timestamp | TTL anchor |
| *(inline)* | AnalysisStep | The area as the phase left it just before validation — prompt, response, token counts, picker and repair telemetry, and its insights with their figures settled and rendered. Deliberately **not** its validation results or its evidence-quality labels: both are produced after validation, by whichever attempt finishes the area |

A marker exists only for an insight the verifier actually ran on. One the per-run validation cap skipped cost nothing and carries none, which is what makes the marker count an exact record of what the area spent of that cap — unlike a completed area, whose `ValidationResults` include the cap-skipped entries and so needs `insights_validated` recorded separately.

The stored insight ids stay live for the whole of the area's in-flight life, so every attempt's markers key on the one set of ids the next attempt reads back. They are reminted when the area is merged into the run's result, which is the point at which they would otherwise collide with what a previous attempt had already persisted.

A draft is superseded by the `AnalysisAreaCheckpoint` for the same area and is deleted when that area finishes — but correctness rests on the reader preferring the completed row, not on the delete, which can be lost to a crash between the two writes.

Indexes: `(run_id, area_id)` unique and a `created_at` TTL named `ttl_discovery_analysis_draft`.

## RecommendationCheckpoint

One in-flight run's **finished Phase 5**. Stored in the `discovery_recommendation_checkpoints` collection, keyed by `run_id`, and the reason a resumed run validates the recommendations a previous attempt generated rather than generating them again.

| Field | Type | Description |
|-------|------|-------------|
| `run_id` | string | The run this checkpoint belongs to (one row per run) |
| `project_id` | string | Project that owns the run |
| `attempt` | int | Which attempt generated these recommendations; the upsert is fenced on it |
| `exploration_attempt` | int | The attempt that wrote the exploration summary the insights behind them were analysed over — the same staleness fence |
| `eligible_insight_ids` | string[] | The insight set Phase 5 was generated over, in the ids the run's analysis checkpoints hold for them. Half the restore gate |
| `analysis_generation` | string[] | Which *analysis* those insights came from — one `area@millis` entry per contributing area, naming the moment that area's analysis ran. The other half of the gate, and the half an insight id cannot carry: an id supplied by the model survives re-analysis, so matching ids do not prove matching findings |
| `rec_verdicts` | object | One validation verdict per recommendation already submitted to the verifier, keyed by the recommendation id as this document holds it. Written one field at a time, for the reason `insight_verdicts` is |
| `created_at` | timestamp | TTL anchor |
| *(inline)* | RecommendationStep | The whole phase — prompt, response, token counts, the parse / citation / figure drop counters, and the surviving recommendations. There is no separate recommendation list, because the step already carries one and the phase resyncs it as recommendations are dropped |

A row exists only for a phase that banked something. A generation call that failed, or a response that could not be parsed, carries none, so a resume retries it. A phase that legitimately produced **no** recommendations does get a row: re-running it costs a real call and the answer is still none, and the step's `status` carries the reason the dashboard renders.

Restoring it is conditional, on two things. First the analysis generation must match: the recommendations have to have been reasoned over the same analysis of every area that contributed to them, which is checked before anything that trusts an id — an insight id is not always server-minted, so a model that repeats one across a re-analysis would otherwise make changed findings look unchanged. Then the ids: a recommendation cites insights by id, and a resumed run mints fresh ids for everything it restores, so `eligible_insight_ids` is compared against the insight set this attempt is actually giving the recommender and every reference — citations and the figure refs that restate an insight's numbers — is translated through the same mapping. If anything fails to resolve, or two eligible insights share a stored id so no translation is unambiguous, the whole row is refused and the recommendations are generated again, because reusing them would describe findings the run no longer has.

The stored recommendation ids stay live until Phase 5.5 returns, so the per-recommendation markers key on one set of ids across attempts, and are reminted before the result is persisted — a recommendation id keys the standalone row and the Qdrant point the tail inserts.

Indexes: `run_id` unique and a `created_at` TTL named `ttl_discovery_recommendation_checkpoint`.
