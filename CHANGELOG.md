## [Unreleased]

### Added

- **CI pushes the `decisionbox-agent` image to AWS ECR** — `.github/workflows/docker-publish.yml`. The Docker publish workflow now pushes the agent image to ECR (`<account>.dkr.ecr.us-east-1.amazonaws.com/decisionbox-agent:<tag>`) after the GHCR push, using OIDC-based AWS authentication. EKS-based deployments can pull the agent image from ECR without cross-registry authentication.

### Fixed

- **Embedding vector dimensions are detected by probing, not a hardcoded catalog** — `providers/embedding/openai/provider.go`, `services/agent/internal/discovery/{dimensions.go (new),schema_indexer.go,phase_embed_index.go}`, `docs/guides/schema-indexing.md`. The agent sized its Qdrant collection from `Embedder.Dimensions()`, which the OpenAI embedding provider derived from a hardcoded model→dims map — `0` for any model the map doesn't know, including a managed-gateway alias such as `decisionbox-embed-model`. That made `agent --mode index-schema` (and Phase 9 embed/index) fail with `dimensions must be positive, got 0`, even though the embeddings themselves were correct. The agent now resolves the dimension robustly: it trusts the provider's declared `Dimensions()` when known (a catalogued model — unchanged fast path) and otherwise **probes** — embeds one short string and uses `len(vector)` — mirroring `run_step_index.go`. Wired into `schema_indexer` (before `EnsureCollection`, so a Qdrant/embedding misconfig still fails fast) and `phase_embed_index`. The OpenAI embedding provider also accepts an explicit `dimensions` config override (flowed in from `project.Embedding.Config`) as an escape hatch for any model/gateway the catalog doesn't know; a non-positive override is rejected. Known models behave exactly as before. Unit + real-Qdrant integration tests cover known-model / unknown-model / gateway-alias / explicit-override.

### Added

- **DecisionBox AI gateway aliases: model pickers + correct max output tokens** — `providers/llm/openai/catalog.go`, `providers/embedding/openai/list_models.go`. When an OpenAI-compatible provider points at the managed DecisionBox AI gateway, its `GET /v1/models` returns aliases (`decisionbox-analysis/blurb/embed-model`) that don't follow OpenAI's naming. The two chat aliases are now catalogued in the OpenAI LLM provider with the **underlying model's output cap** — `decisionbox-analysis-model` → Opus's 128K, `decisionbox-blurb-model` → the blurb model's 64K — instead of the provider's generic 16K default, so callers that size a request from `GetMaxOutputTokens` no longer truncate a large generation; cataloguing also surfaces them (dispatchable) in the LLM picker. The embedding picker keeps the embed alias by requesting `?type=embedding` and keeping any row that is `text-embedding-*` or gateway-owned (`owned_by: decisionbox`). No shared registry/handler or frontend changes.

- **Real end-to-end tests through the DecisionBox AI gateway** — `services/agent/agentserver/{gateway_e2e_test.go,index_schema_e2e_test.go}` (new, `-tags e2e`). Env-gated, no mocks: the pickers list the gateway aliases and a chat dispatches through the analysis alias over the OpenAI wire; the production `runIndexSchema` pipeline indexes a BigQuery warehouse (the olist demo by default) — discover schemas → resolve dimensions → blurbs through the gateway alias → embed → Qdrant upsert. Set `DBX_GATEWAY_URL` / `DBX_GATEWAY_KEY` (+ `DBX_E2E_INDEX=1` and the warehouse/Qdrant/AWS env) to run against `ai.decisionbox.io`.

## [0.11.0] - 2026-06-09

### Added

- **Short, consistent SQL dialect label in warehouse `ProviderMeta`** — `libs/go-common/warehouse/registry.go`, `providers/warehouse/{bigquery,databricks,mssql,postgres,redshift,snowflake}/provider.go`, `services/api/apiserver/warehouse_dialect_test.go` (new), `ui/dashboard/src/lib/api.ts`, `docs/concepts/providers.md`, `docs/guides/adding-warehouse-providers.md`, `docs/reference/api.md`. Adds a new `ProviderMeta.Dialect` field — a short, clean dialect label (`"BigQuery Standard SQL"`, `"Snowflake SQL"`, `"PostgreSQL"`, `"Amazon Redshift SQL"`, `"Databricks SQL"`, `"T-SQL"`) declared by every registered warehouse provider at registration. Unlike `warehouse.Provider.SQLDialect()` — which returns a verbose, prompt-oriented description and requires a *constructed* provider (and therefore config/credentials) — this label is available by slug with no instantiation via `GetProviderMeta(slug)` / `RegisteredProvidersMeta()` (and the `GET /api/v1/providers/warehouse` listing, which now includes a `dialect` field), so display / metadata / registry-driven UI can read a stable dialect label without building a provider. `SQLDialect()` behaviour is unchanged.

- **`docker` agent runner mode — spawn the discovery agent as its own container** — `services/api/internal/runner/{docker.go (new),docker_test.go (new),docker_integration_test.go (new),env.go (new),runner.go,kubernetes.go}`, `services/api/internal/server/server.go`, `services/api/apiserver/systeminfo.go`, `services/api/go.mod`, `Makefile`, `.github/workflows/ci.yml`, `docker-compose.yml`, `docs/reference/configuration.md`, `docs/deployment/docker.md`. Adds a third `RUNNER_MODE` alongside `subprocess` and `kubernetes`: `docker` spawns each agent invocation as its own short-lived container from `AGENT_IMAGE` via the Docker engine (official Docker SDK over `DOCKER_HOST` / the mounted socket), giving docker-compose / single-host deployments the same "API spawns the agent from a configurable image" model the Kubernetes runner provides — without a cluster. It closes the gap for setups where the agent image must differ from the API image (so subprocess mode cannot run it) or that want production-like API/agent isolation locally. All five `Runner` methods are implemented (`Run`, `RunSync`, `RunIndexSchema`, `RunValidateDoc`, `Cancel`) with the same agent CLI args the other runners build; container logs stream to the API log and to the live-tail `OnLogLine` callback; non-zero exit surfaces via `OnFailure`; `Cancel` SIGTERMs the container then removes it — the same graceful termination a K8s pod gets on cancel (mirrors the K8s foreground delete; persisting partial results on SIGTERM additionally needs agent-side signal handling, tracked separately). Each agent container is attached to a configurable `AGENT_DOCKER_NETWORK` so it resolves `mongodb` / `qdrant` / warehouse hosts by service name, labelled (`run-id`, `project-id`) for discoverability, and removed on completion; a missing image is pulled (with a clear error if neither present nor pullable — a missing `AGENT_DOCKER_NETWORK` is surfaced distinctly, not masked as a pull failure) and an unreachable socket fails fast at startup. A backgrounded run is bounded by `AGENT_JOB_TIMEOUT_HOURS` (the Docker analogue of the K8s Job `ActiveDeadlineSeconds`): on expiry the container is force-stopped and the run failed, so a wedged agent can't run forever. On startup the runner reaps agent containers orphaned by a prior API crash/restart (Docker has no daemon-side Job TTL), and `Cancel` removes the container itself rather than relying on the in-process watcher and marks the run so the watcher reports the resulting exit as a cancellation, not a failure (mirrors the K8s watcher going silent after a Job delete). A failed `RUNNER_MODE=docker` / `kubernetes` init (e.g. an unreachable socket) now fails API startup instead of silently downgrading to the in-process subprocess binary. The agent container receives the curated Mongo / secret-provider / Qdrant / validation passthrough shared with the Kubernetes runner (extracted to a shared `env.go` — no behaviour change to the existing modes), plus docker-only passthrough of AWS + Azure credentials, the LLM behaviour knobs (`LLM_TIMEOUT`, `LLM_MAX_RETRIES`, `LLM_REQUEST_DELAY_MS`, `LLM_RETRY_*`), `ENV` / `LOG_LEVEL`, and the telemetry opt-out (`TELEMETRY_ENABLED`, `DO_NOT_TRACK`). LLM API keys are never forwarded (loaded from the secret provider), and `GOOGLE_APPLICATION_CREDENTIALS` is deliberately not forwarded — it is a file path the runner cannot bind-mount into the sibling agent container, so GCP credentials must reach the agent via the host metadata server / Workload Identity or a custom `AGENT_IMAGE`. The System inventory (`GET /api/v1/system`) reports the `AGENT_IMAGE` tag in docker mode (like kubernetes) instead of the bundled-binary version. **Security:** mounting the Docker socket grants root-equivalent host access — docker mode is documented as a local / single-host convenience; production should use the `kubernetes` runner.

- **Generic `--mode=validate-sql` batch SQL compile-check run mode** — `services/agent/agentserver/agentserver.go`, `services/agent/agentserver/{validate_sql.go,validate_sql_check.go}` (new), `services/api/models/sql_validation_job.go` (new), `services/api/database/sql_validation_job_repo.go` (new), `services/api/database/init.go`, `docs/reference/{cli.md,configuration.md}`, `Makefile`. Adds a warehouse-agnostic agent Job mode that compile-checks a batch of SQL statements against a project's configured warehouse and writes the verdicts back to Mongo — so any caller can confirm the warehouse accepts a candidate query **without opening a warehouse connection in the calling process** (the platform invariant that only the agent talks to warehouses). It mirrors the existing `validate-doc` Job pattern: a `sql_validation_jobs` row carries `{project_id, statements[]}`; the agent (`agent --mode=validate-sql --job-id <id>`) atomically claims it, builds the project's warehouse provider via the same `initWarehouseProvider` path discovery uses, runs each statement through `warehouse.Provider.ValidateSQL` (the warehouse's native compile-only path — BigQuery `DryRun`, PostgreSQL/Redshift/Databricks `EXPLAIN`, Snowflake `EXPLAIN USING TEXT`, SQL Server `SET NOEXEC ON`), and records one `{sql, ok, error}` verdict per statement before marking the job complete. Validation is **compile-only and never executes the statement** — a `DELETE`-shaped statement compiles to `ok:true` but changes no rows (verified by the integration test's before/after row count). Read-only safety rests on the project's warehouse credentials being read-only (the platform's expectation for every connection); this mode does no SQL parsing of its own. Provider-construction or job-level failures fail the run (non-zero exit, `error` on the job doc); per-statement compile failures are recorded as `{ok:false, error:<warehouse's own message>}`, not a job-level failure. Unlike `validate-doc` (claimed by an in-API worker) there is no HTTP surface and no worker: a caller enqueues via the new `database.SQLValidationJobRepo` (`Enqueue`/`GetByID`), dispatches the agent, and polls Mongo (and owns stale-recovery for a crashed run). Oversized batches are bounded by `SQL_VALIDATION_MAX_STATEMENTS` (default 500; `0` disables). A 60s heartbeat keeps the job row live during long batches.

### Fixed

- **BigQuery cross-project reads now generate resolvable SQL (`bigquery-public-data` shape)** — `providers/warehouse/bigquery/provider.go`, `libs/go-common/warehouse/provider.go`, `services/agent/internal/discovery/schema_discovery.go`. When **Data project ID** differs from **GCP Project ID**, every exploration query failed with `404 … Dataset <jobs-project>:<dataset> was not found in location …`. Root cause: the agent showed the model two-part `dataset.table` names, and BigQuery resolves the *project* of a two-part reference to the query-job (billing) project — never to a default dataset's project. The previous `Query.DefaultProjectID`-only approach could not fix this — the SDK ignores a project-only default (it requires `DefaultDatasetID` too), and even with both set a two-part ref still resolves to the jobs project; only a fully-qualified three-part name (or a bare name + default dataset) resolves to the data project. Fix: the BigQuery provider now emits fully-qualified three-part `data-project.dataset.table` references everywhere the model sees a table — the schema catalog / cache key (via the new optional `warehouse.RefQualifier` interface), `{{REF:…}}` and sample-query rendering (`QuoteRef` / `SampleQuery`) — and sets both `DefaultProjectID` and `DefaultDatasetID` so a bare `table` reference still resolves. Single-project setups (Data project ID empty) are byte-for-byte unchanged. **Existing cross-project projects must re-index their schema** so the cache picks up the three-part names.

### Added

- **Generic background-jobs surface for plugin-spawned long-running goroutines** — `services/api/apiserver/background_jobs.go`, `services/api/apiserver/apiserver.go`, `helm-charts/decisionbox-api/{templates/deployment.yaml,values.yaml}`. Adds `apiserver.SpawnBackgroundJob(fn func(ctx context.Context)) error` so a plugin HTTP handler can hand off work to a goroutine whose lifetime is the API process (not the inbound request's context). The new ctx is a process-level `context.WithCancel(context.Background())` that the apiserver cancels at the start of shutdown; the WaitGroup behind it is what the new shutdown drain blocks on. Shutdown sequence is now `srv.Shutdown (10s) → shutdownBackgroundJobs (15s, bounded) → deferred Mongo disconnect` — HTTP drains first so no new inbound request can register a goroutine that misses the WaitGroup, then the bounded drain waits for in-flight cleanup writes to land while Mongo is still connected. `SpawnBackgroundJob` returns `ErrBackgroundJobsShutdown` once the registry has entered shutdown; callers must propagate the error rather than silently swallowing it — the goroutine would otherwise race the Mongo disconnect. The mutex + atomic flag inside the lazy singleton blocks the classic "Add after Wait" race. The Helm chart now sets `terminationGracePeriodSeconds: 45` (was relying on the K8s default 30s) — the new value covers the 25s worst-case wall-clock drain plus 20s of slack for signal delivery, Go scheduler latency, kubelet variance, and Mongo round-trip; override-able via `.Values.terminationGracePeriodSeconds`. Tests in `background_jobs_test.go` cover happy-path completion, post-shutdown-spawn rejection, bounded-wait-on-stuck-goroutine, idempotent double-shutdown, concurrent fan-out, ctx cancellation propagation, and the spawn-just-before-shutdown race.

### Fixed

### Added

- **`warehouse.Provider.ValidateSQL` — dialect-aware compile-only SQL check** — Every warehouse provider gains a `ValidateSQL(ctx, sql) error` method on the `warehouse.Provider` interface. Each implementation routes through the warehouse's native compile-only path so the dialect-owner decides whether the statement parses, resolves names, and compiles: BigQuery uses `QueryConfig.DryRun = true`; PostgreSQL, Redshift, and Databricks use `EXPLAIN <sql>`; Snowflake uses `EXPLAIN USING TEXT <sql>`; SQL Server uses `SET NOEXEC ON; <sql>; SET NOEXEC OFF;` (PARSEONLY only applies to subsequent batches in T-SQL, so it cannot gate a same-batch INSERT — confirmed by integration test). All six providers reject empty / whitespace-only SQL at the boundary, wrap the warehouse's own error with a `"<provider>: validate SQL: %w"` prefix so the underlying message is preserved alongside the routing context, and explicitly do not execute the statement. Read-only enforcement remains `ValidateReadOnly`'s responsibility — passing `ValidateSQL` on a write statement does not authorise execution. Unit tests cover the boundary check, the wire-format expectations, and error propagation for every provider; integration tests behind the existing per-provider build tags exercise the real compile path on Postgres (testcontainers), BigQuery (real), Redshift (real), and SQL Server (testcontainers). Snowflake and Databricks ship unit-only coverage until test accounts are available. **Pre-1.0 break:** any out-of-tree `warehouse.Provider` implementation must add the new method.

- **Per-attempt SQL fix history on `ExplorationStep`** — `ExplorationStep` gains a `fix_history` field carrying one `FixAttempt` entry per LLM call the self-healing SQL fix loop made for that step. Each entry records the rendered fix prompt, the raw LLM response, the broken SQL, the proposed fix, the warehouse error that triggered the call, the parent step number, and token / latency accounting. Every attempt is logged — including failed attempts (LLM transport error, unparseable response, post-fix security-filter rejection), which carry `FixerError` set so downstream tooling can distinguish applied repairs from negative examples. `FixAttempts` counts only applied repairs (`FixerError` empty), so `FixAttempts <= len(FixHistory)`. The `queryexec.SQLFixer` interface return type changed from `(string, error)` to `(queryexec.FixResult, error)` and `QueryExecutor.Execute*` now returns a non-nil partial `*ExecuteResult` on every error path so callers can read accumulated history (pre-1.0 break, no shim). Plugins implementing `SQLFixer` need to adjust their return shape.
- **SQL fixer reads `MaxOutputTokens` from the LLM model catalog** — `services/agent/internal/ai/sql_fixer.go` no longer hard-codes `4000` for every model. The cap is now resolved via `gollm.GetMaxOutputTokens(provider, model)`, so wider-window models (GPT-5 family at 32K+, Claude 4.x at 16K+) get the cap their catalog entry declares, and unknown providers fall back to the 8192 global default. Fixes an observed failure mode where Gemma3 was hitting the 4000 cap and returning truncated unparseable responses.
- **Plugin route-group extension point** — `apiserver.RegisterRouteGroup(prefix, handler)` lets plugins built on top of the community API server mount additional HTTP routes on the authenticated mux from `init()`, without modifying the core router. Each group is mounted at `{prefix}/` and flows through the API server's global auth + RBAC chain. Empty / non-leading-slash / trailing-slash / nil-handler / duplicate-prefix registrations panic at boot so typos fail noisily. Documented under [Plugin Hooks → Hook 6](docs/concepts/plugin-hooks.md#hook-6--plugin-route-groups).
- **External model registry extension point** — A new `catalog.Extender` interface in `libs/go-common/llm/catalog/` lets plugins surface additional `gollm.ModelEntry` rows for the dashboard model picker (`Extend(ctx, projectID) []ModelEntry`) and answer opaque-model-ID resolution queries (`Resolve(ctx, modelID) (*ModelEntry, error)`). Registered via `catalog.RegisterExtender(...)` from `init()`. A new project-scoped endpoint `GET /api/v1/projects/{id}/llm/extended-models` exposes the concatenated extender results in the same shape as built-in catalog rows so the dashboard can merge both without reshaping. Returns an empty list on the default community build (no extenders registered). Documented under [Plugin Hooks → Hook 7](docs/concepts/plugin-hooks.md#hook-7--external-model-registry).

### Fixed

- **BigQuery provider supports cross-project reads (`data_project_id`)** — `providers/warehouse/bigquery/provider.go`. BigQuery has two project axes that don't have to match: the project whose principal runs the query job (needs `bigquery.jobs.create`) and the project that owns the dataset (needs only read access). The provider used to collapse them onto a single `project_id` field, so operators who wanted to query `bigquery-public-data` samples couldn't: setting `project_id=bigquery-public-data` made the schema indexer work (metadata reads don't need `jobs.create`) but every actual query job failed with `403 Access Denied: User does not have bigquery.jobs.create permission in project bigquery-public-data`, and setting `project_id=my-billing-project` failed health check with `404 Not found: Dataset my-billing-project:google_analytics_sample`. The provider now exposes an optional `data_project_id` field — empty for single-project setups (behaviour identical to before), set to the dataset's home project when reading datasets the operator doesn't own. When set, DecisionBox constructs the BigQuery client against `project_id` so jobs bill there, routes metadata reads to `data_project_id` via `client.DatasetInProject(...)`, and sets `Query.DefaultProjectID = data_project_id` so unqualified `dataset.table` references in agent-generated SQL resolve against the data project rather than the jobs project. Four new tests pin the wiring (default-to-project-id, explicit value preserved, factory pass-through, config-field schema surface); the existing test suite stays green. Docs: `docs/guides/configuring-warehouse.md` gains a "Cross-Project Reads" subsection with the `bigquery-public-data` example.

- **Vertex / Azure-Foundry / Bedrock now accept empty `model` at factory construction for list-only mode** — `providers/llm/vertex-ai/provider.go`, `providers/llm/azure-foundry/provider.go`, `providers/llm/bedrock/provider.go`. Following the precedent the Ollama provider already set (PR #226's "lister or empty, never error" contract), these three providers no longer reject `cfg["model"] = ""` at factory time. The `model is required` check moved into `Chat()` and `Validate()` where it surfaces as a typed `"constructed without a model (list-only construction)"` error. Without this, the dashboard's "Load models" flow — which strips `cfg["model"]` before factory construction because the model field is irrelevant to `ListModels()` — silently returned `(nil, nil)` from `fetchLiveModels` because the factory always errored on the missing model. The dashboard then fell back to the static catalog and live-list never ran for Vertex / Azure / Bedrock; the upstream's actual model list (e.g. Gemini preview models on Vertex) was invisible to the operator. Now the factory constructs successfully, `ListModels()` is reached, and the upstream's catalogue lands in the picker. Tests pin both the construction-success contract and the runtime-Chat-refusal guardrail for each provider.

- **LLM model picker is live-list-only — the shipped catalog is no longer offered as default selection options** — `ui/dashboard/src/components/common/LLMModelField.tsx`. The legacy `ModelCombobox` that surfaced every provider's hard-coded catalog as a dropdown is gone. The `model` field now renders a plain free-text input by default; the live-list dropdown (`LiveModelCombobox`, already used by every project-create / settings surface) remains the canonical picker after the operator clicks "Load models". The shipped catalog still enriches typed values with wire / pricing metadata inside `LiveModelCombobox` (the badges next to a chosen row) so dispatch + cost estimation still work for any catalogued ID, but new / preview / customer-specific model IDs are typed verbatim. Removes the long-standing "see Claude Opus 4.6 listed but no Gemini 3.x preview" inconsistency that surfaced whenever the shipped catalog lagged the upstream's actual offering.

- **Schema-index blurb generation gets a higher MaxTokens budget (512 → 8192) + a `BLURB_MAX_TOKENS` env-var override** — `services/agent/internal/discovery/blurb/blurb.go` + `services/agent/agentserver/index_schema.go`. The previous 512-token budget was sized for non-thinking blurb models (Haiku-class), but modern "thinking" models — Gemini 2.5+ Pro / 3.x preview, Qwen3 with default thinking-on, GPT-5-mini, etc. — emit a hidden reasoning preamble before producing the visible answer. On large-schema tables (100+ columns) and on thinking models in general, that preamble consumes the entire 512-token budget before the visible blurb starts, the model returns `finish_reason=MAX_TOKENS` (or `length` for OpenAI-compatible providers) with empty content, and the retry classifier correctly skips the retry as deterministic — leaving every such table failed. 8192 is roomy enough for a thinking preamble + a 2-4 sentence visible blurb across the full range of warehouse shapes we've seen in practice (ERP-scale 200+ column tables included); operators can crank further via `BLURB_MAX_TOKENS=N` for outsized custom prompts or drop it for cost control on a cheap non-reasoning blurb model. Token cost only accrues to what the model actually emits, not the cap — so non-thinking models still pay for their ~200-token blurbs and not for the extra 8K of headroom. Resolves a live failure where 34 of 369 tables consistently failed on both `gemini-3.1-pro-preview` and Ollama `qwen3:32b` — same exact tables, same exact count, regardless of provider — because the failure was budget exhaustion, not model behaviour.

- **Pack-generation home-page copy now names pack synthesis as a separate, still-pending step after schema indexing completes** — `ui/dashboard/src/components/projects/PackGenStatusPanel.tsx`. Before this fix the home page's `pack_generation_pending` + `indexStatus=ready` state showed a green "Schema indexed" badge + "Schema index is ready. Continue in the wizard to upload knowledge sources, review the pack description, and launch the agent" + a "Continue setup" button — too optimistic for operators who read the badge and assumed pack generation was complete. They got stuck waiting for a "Start discovery" affordance that never materialises in this state. The new copy spells out the two-step lifecycle at every glance: badge becomes "Schema indexed — step 1 of 2", helper copy explicitly says "Pack synthesis (step 2) has not started yet: click Launch pack generation below to start it", button label becomes "Launch pack generation" — onClick POSTs to `/api/v1/projects/{id}/pack-generate` directly when every pre-condition holds (pack_gen_last_error empty + generate_pack populated + indexReady), refreshes the project doc so the home page flips to the synthesis view immediately, and falls back to the wizard route with "Open wizard to launch pack" when any pre-condition is missing. The indexing-in-flight badge gains the same step disambiguator ("Indexing schema (step 1 of 2)" + "Step 1 of 2 — schema indexing is running"). The wizard-resume case (no warehouse + no index) keeps its existing "Continue setup" + "Pick up where you left off…" copy since that state has no step ambiguity to resolve.

- **Schema-index blurb generation retries transient empty responses + surfaces the finish reason on hard failures** — `services/agent/internal/discovery/blurb`. Each per-table blurb call now runs up to two attempts: the first covers the happy path, the second absorbs transient failures (empty responses with no `finish_reason` hint, network blips, 429s, brief 5xx). The classifier `blurbErrorRetryable` skips the retry for deterministic empty reasons (`SAFETY`, `RECITATION`, `MAX_TOKENS`) so the operator's wall-clock + token budget aren't wasted on prompts the model will keep refusing — those surface immediately with `finish_reason=<REASON>` in the error so the fix is obvious (raise `MaxTokens`, pick a different model, edit the prompt). Runaway-response failures (over `MaxBlurbLen`) also skip the retry — they're deterministic for a given prompt at `temperature=0`. Backoff between attempts is 500ms with a `ctx.Done` short-circuit so a cancelled run doesn't burn workers staring at sleep. Resolves a live failure mode on Gemini preview models where 34 of 369 blurbs returned empty under no obvious cause and tripped the default 5% failure budget; the retry absorbs the transient cohort, leaving only the genuinely deterministic refusals to surface with diagnostic context.

- **Project home page surfaces schema-indexing progress while a pack-generation draft is still pending** — `ui/dashboard/src/components/projects/PackGenStatusPanel.tsx`. When a project is in `pack_generation_pending` state and the operator has clicked "Build schema index" inside the pack-generation wizard, the home page now mounts the same `SchemaIndexPanel` it uses during `pack_generation` and drives the title badge + helper copy from the panel's status callback: gray "Pending" → blue "Indexing schema" → green "Schema indexed", or red "Indexing failed" / orange "Indexing cancelled" / orange "Re-index required". The "Continue setup" button label flips to "Open wizard to retry" on failed / cancelled / needs_reindex. The panel mount is gated on a fully-configured warehouse (`provider` AND at least one dataset) OR an existing in-flight / terminal status, so a fresh pack-generation draft with no warehouse stays on the wizard-resume prompt without exposing a Build-schema-index action that would enqueue a doomed indexing run. Before this fix the home page only showed the static "Pick up where you left off in the wizard" copy and forced the operator into the wizard's final step to monitor the worker; the home page is now the natural progress surface, matching what the `pack_generation` two-step view already does for indexing during synthesis. Existing `pack_gen_last_error` banner + "Retry in wizard" button label are preserved — a prior synthesis failure dominates the badge over the schema-index status.

### Changed (pre-1.0 break — operator action not required, but UX shifts)

- **Live-list endpoints (LLM + embedding) now follow "lister or empty, never error"** — `POST /api/v1/providers/llm/{id}/models/live`, `POST /api/v1/projects/{id}/providers/llm/models/live`, and the embedding equivalents previously injected a placeholder model (`"list-only-placeholder"` for LLM; `meta.Models[0].ID` — typically `nomic-embed-text` — for embedding) to get past factory-side runtime validators that require a model. The injection caused the Ollama embedding factory to probe the placeholder model upstream and 404 if it wasn't pulled, after which the dashboard silently fell back to the static catalog and hid the models the server actually had. The new contract: strip `cfg["model"]` before factory construction (the model field is irrelevant to every supported list API), return `(nil, nil)` when the factory rejects the empty model or the provider doesn't implement `ModelLister`. Real upstream errors from a working `ListModels()` call still propagate. The dashboard's "Load models" button now reliably shows what the server reports, and falls back to free-text + catalog when listing isn't supported.
- **Ollama LLM and embedding factories now accept an empty `model`** — list-only construction. Embed/Chat/Validate on a list-only provider return a clear "constructed without a model" error instead of forwarding empty to the upstream API. Required to make the new live-list contract work for Ollama, which (uniquely) probes the supplied model at construction time.

### Fixed

- **AWS Bedrock `ListFoundationModels` now uses the project's auth method** — `providers/llm/bedrock/list_models.go` and `providers/embedding/bedrock/list_models.go` were calling `awsconfig.LoadDefaultConfig` to build their own control-plane client, bypassing the per-project `auth_method` (access_keys / assume_role / iam_role) the factory had already resolved via `libs/awscreds`. ### Fixed

- **Ask sessions no longer fail with a misleading "embedding not configured" message after 3–5 turns** — The handler in `services/api/internal/handler/search.go::Ask` previously hard-trimmed conversation history to the last 10 turns with no awareness of message length or model context window, so by turn 5 of a normal session the upstream provider could 4xx with `invalid_request_error: prompt is too long`. Every non-2xx from the provider was then mapped to a flat HTTP 500 with the generic error `"LLM synthesis failed"`, which the dashboard rendered as `"Sorry, I could not answer this question. Make sure embedding is configured for this project."` — a copy-paste that suggested the wrong root cause (embedding, not context). The handler now sizes every Ask call against the model's published `MaxInputTokens`, subtracts `max_tokens` (the 2048-token generation reserve) and ~600 tokens for the system prompt, then trims session history newest-first by token count rather than turn count. Insights are dropped lowest-scoring-first if the retrieved context alone wouldn't fit. The trim invariants are: never separate a user message from its assistant reply (no orphan assistants), the current user question always rides at the end, and the safety margin widens from 5% to 15% when the active counter is approximate so under-counting can't push us past the upstream cap.

- **Agent K8s Job pods satisfy PodSecurity `restricted` admission** — `KubernetesRunner.buildJob()` now stamps a full pod + container `SecurityContext` (`RunAsNonRoot=true`, `RunAsUser/Group=1000`, `FSGroup=1000`, `AllowPrivilegeEscalation=false`, `ReadOnlyRootFilesystem=true`, `Capabilities.Drop=[ALL]`, `SeccompProfile.Type=RuntimeDefault`) on every Job it creates (discovery runs, schema indexing, test-connection). Without these fields, namespaces labeled `pod-security.kubernetes.io/enforce=restricted` reject every agent Job and the dashboard shows "Schema index: Not indexed" indefinitely. To keep `ReadOnlyRootFilesystem=true` compatible with cloud SDKs that opportunistically write disk caches (gosnowflake OCSP, AWS/GCP token files), the spec also declares an `emptyDir` volume mounted at `/tmp` and points `TMPDIR=/tmp` + `HOME=/tmp`. The agent image (Alpine + static Go binary) already runs as UID 1000 with no capabilities — this is a spec-only fix with no runtime behavior change.

Resolution is catalog → ProviderMeta `DefaultMaxInputTokens` → package-level `DefaultMaxInputTokens = 32000` so unknown models still get a usable (conservative) budget.   - **OpenAI direct** via `gollm.NewTiktokenCounter` (factored out into `libs/go-common/llm/tiktoken_counter.go` so any OpenAI-wire provider can reuse it). ## [0.5.0] - 2026-05-15

### Added

- **Platform-enforced claim-discipline rules appended to every writer and verifier prompt at runtime** — A new `services/agent/internal/discipline` package owns four exported rule blocks (base context, analysis, recommendations, verifier) that the orchestrator and the insight validator append to their respective prompts immediately before sending to the LLM. The rules cover scope-binding superlatives, no-claim-beyond-query-window, re-ranking from raw result rows, addressing counter-evidence explicitly, cross-field self-consistency, citing the step for every number, partial-period hygiene, and objective non-dramatic prose (principle + worked Bad → Good examples, no enumerated banned-words list). The verifier block additionally carries V1–V4 rules that funnel through the existing count-comparison pipeline: V1 instructs the LLM to construct ranking SQL whose returned `count` encodes claim correctness (`SELECT CASE WHEN actual_top = claimed_top THEN <claimed> ELSE 0 END AS count`); V2/V3/V4 emit `SELECT 0 AS count` with an in-SQL comment naming the offense, so the existing `count == 0 → rejected` branch fires with a logged reason. **Why in code, not in pack files:** user-added custom analysis areas (created via the dashboard or `PUT /api/v1/projects/{id}/prompts`) carry no pack content; user-edited or generator-produced packs can drop the rules by accident; the rules survive any pack-authoring path. The rule text is intentionally language-neutral — every rule block carries an explicit "LANGUAGE NOTE" telling the LLM to apply the same constraints to the project's configured output language (the English examples are illustrations of the principle, not the principle). The three orchestrator injection sites in `services/agent/internal/discovery/orchestrator.go` (base context after substitution, each analysis-area prompt after assembly, recommendations prompt after assembly) call `discipline.AppendBaseContextRules` / `AppendAnalysisRules` / `AppendRecommendationsRules`; the verifier wires `discipline.VerifierRules()` into `buildVerificationPrompt`'s `fmt.Sprintf`. No model schema change, no template-variable change, no backfill migration — code-level injection makes every existing project benefit on its next run regardless of stored prompt content. Coverage: 18 unit tests in `discipline/rules_test.go` (rule-text shape, leading markdown header, language-neutrality, output-language clause, deterministic returns, no leftover template variables, valid UTF-8, non-overlapping section headers, Append helpers' double-newline separator + empty-input + double-call behavior + custom-area regression with empty / multi-line / unsubstituted / non-Latin payloads), plus 5 validator tests in `insight_validator_discipline_test.go` covering single-shot mode, loop mode, lookup-notice path, preservation of the existing prompt contract (datasets header, dialect header, `AS count` alias, `COUNT(DISTINCT user_id)`, fully-qualified table refs), and a regression test fixture for the case-study insight that motivated the work. - **Discovery run completion plugin hook** — A new fifth plugin hook (`apiserver.RegisterRunCompletionHook`) fires once per discovery run that reaches a terminal state (`completed`, `failed`, or `cancelled`). Hooks are sequential within a run (an audit-record hook finishes before a downstream notifier observes it) and resilient (a hook that panics is recovered with a panic-tagged error; sibling hooks still run). - **User-count probe routed through the self-healing executor with grounded `FixOpts`** — `services/agent/internal/validation/user_count_validator.go` used to issue three hardcoded `COUNT(DISTINCT user_id) FROM <table>` probes via the raw warehouse client, and silently gave up when none matched the warehouse's column conventions — letting every insight's affected_count claim through unverified on warehouses with non-`user_id` user-id columns (e.g. `KULLANICI_ID`, `customer_id`, `USER_ID_HASH`). The validator now takes an optional `Executor` (the same `SelfHealingExecutor` interface the insight validator uses) and forwards a rendered `FixOpts.VerificationContext` on every probe call. The context is built from the union of all `query_data` step IDs in the exploration log — run-wide evidence, since the user-count probe is single-shot per run rather than per-insight. When the hardcoded `user_id` probe fails with `Invalid column`, the SQL fixer sees the source-step SQL and substitutes the real column name on retry. Without an `Executor` wired, the validator falls through to direct `warehouse.Query` (legacy behaviour preserved for tests and the orchestrator's pre-RunDiscovery construction window). Layer 4 of the verification-grounding fix.

- **Verifier owns a `lookup_schema` tool loop for cross-table grounding** — The insight verifier is no longer a single-shot LLM call. With a `SchemaProvider` wired (Layer 3 of the verification-grounding fix), it runs up to `MaxLookupsPerVerification = 6` `lookup_schema` rounds per insight before emitting the final SELECT COUNT — letting the model fetch column detail for tables that `source_steps` did not cover. Lookup results land in the rendered `VerificationContext` after the source-queries block, so the SQL fixer benefits from the same evidence on retry. A shared action parser (`ai.ParseAction(response, allowed)`) takes an allow-list — the explorer's `parseAction` becomes a thin wrapper passing `nil` (any action), the verifier passes `[]string{"lookup_schema", "query_data"}` so the model can't "complete" mid-verify and explorer-only future actions don't silently leak in. When the lookup budget is exhausted before the model emits a query, one forced final round (NOT counted against the budget) is allowed; failure to emit a query after that surfaces as `validation.status="error"` with a clear telemetry signal rather than reusing an arbitrary fallback. Without a `SchemaProvider` wired, the verifier falls through to a single-shot generation (Layer 1 + 2 only). Implementation: new `runVerificationLoop` in `services/agent/internal/validation/insight_validator.go`, new `RenderVerificationContextWithLookups` in `services/agent/internal/validation/render`, `(e *ExplorationEngine).extractJSON` lifted to a free function alongside `ai.ParseAction`. - **Self-healing SQL fixer carries per-call verification context** — `SQLFixer.FixSQL` takes a new `queryexec.FixOpts` argument with a `VerificationContext` field. - **Insight verifier grounded on cited source-step SQL** — The insight verification phase used to receive only the table-level catalog (one line per table, no column names). - **Analysis phase: vector-ranked step selection + per-step compact digest** — The analysis phase no longer ships every keyword-matched exploration step's full `query_result` blob into the LLM prompt. On ERP-scale runs that approach hit a 1.4M-token prompt that Bedrock Claude rejected outright (`prompt is too long: 1401958 tokens > 1000000 maximum`), and the affected areas produced 0 insights. Two changes ship together: every exploration step is now indexed inline into a per-run Qdrant collection (embedding text = step purpose + SQL), and the analysis loop ranks steps per area by vector similarity to the area's identity (Name + Description + Keywords) plus a verbatim-keyword exact-match boost. - **Schema cache write no longer fails on wide-row warehouse tables** — On data-warehouse-class tables backed by `VARCHAR(MAX)` / `XML` / `JSON` / `VARBINARY` / wide nested-struct columns (Oxxo MSSQL DW, FINPORT-class), a single `SELECT TOP 5 *` sample row routinely exceeds 1 MB; five sample rows × even modest column counts trip Mongo's hard 16 MB BSON document limit on the `project_schema_cache` write. The indexer logged the failure as a warning (`schema_indexer: schema-cache save failed; next run will rediscover`) and continued, leaving `schema_index_status: ready` while `project_schema_cache` was empty for the project — every subsequent discovery run failed with `schema cache lookup failed: schema cache is empty for this project`. `SchemaCacheRepository.Save` now caps cached sample rows at 3 per table and truncates each string / `[]byte` value before insertion: text-shaped values (Go `string` and UTF-8 `[]byte`) are truncated at a **rune boundary** to 256 runes (so multi-byte UTF-8 codepoints are never split — BSON rejects invalid UTF-8) with the marker `…(truncated, original N chars)`; non-UTF-8 `[]byte` (typical for `VARBINARY` / `BLOB` / `FILESTREAM`) is **base64-encoded** at the 256-byte prefix with the marker `…(truncated binary, original N bytes, base64)` so the cache row stays storable as a BSON string without losing fidelity. Non-string values (numbers, bools, time.Time) pass through. New unit tests pin the contract (`schema_cache_repo_test.go`) including a Turkish multi-byte-rune split regression, a non-UTF-8 binary round-trip via base64, and an adversarial 1000-distinct-column × 6-row × oversized-value case that asserts the capped output stays comfortably under the 16 MB cap.

Without this fallback, an `us.anthropic.claude-opus-4-7-v1:0` lookup missed the catalog and `llm.GetMaxOutputTokens` fell through to the provider's `_default` of 16384 — small enough that an Opus 4.7 pack-generation synth (full DomainPack JSON, 271k-char prompt) truncated mid-output, retried, and ran past the dashboard's 5-minute proxy budget. Bedrock now correctly resolves the 128k Opus cap (and 64k Sonnet/Haiku caps, 32k legacy Opus 4 cap) for every cross-region inference profile alias of an already-catalogued model. The strip is Bedrock-specific so Vertex / Azure model IDs that happen to start with `us.` or `global.` are unaffected.

- **Schema discovery no longer costs one LLM call per table on non-BigQuery warehouses** — `SchemaDiscovery.getSampleData` used to emit a hardcoded BigQuery/MySQL-style query (`` SELECT * FROM `dataset.table` … LIMIT 5 ``) for every warehouse provider, which fails on T-SQL (MSSQL), PostgreSQL/Redshift/Snowflake (double-quoted identifiers), and any dialect without `LIMIT`. The SQL fixer would rewrite it per table — an extra Claude round-trip (~5s + ~8 KB input tokens) for every table in the warehouse before the first sample could be fetched. New optional `warehouse.SampleQueryBuilder` interface in `libs/go-common/warehouse` lets a provider supply its own dialect-native sample query. All six community providers implement it: BigQuery (`` `dataset.table` `` + `LIMIT`), MSSQL (`SELECT TOP 5 * FROM [schema].[table]`), PostgreSQL and Redshift (`"schema"."table"` + `LIMIT`), Snowflake (`"SCHEMA"."TABLE"` + `LIMIT`, preserving case), Databricks (`` `schema`.`table` `` + `LIMIT`). Providers that don't implement it still fall back to the BigQuery-style legacy — behaviour for any third-party provider is unchanged. Unit tests per provider + schema-discovery routing test covering both the builder and fallback paths.

- **Exploration terminated after 2–18 steps on reasoning-model LLMs** — The exploration response parser treated any response it couldn't cleanly decode as a "complete" signal: JSON without `query`/`done`/`action` was silently assumed done, and responses with no JSON fell through to a plain-text substring match on `"done"` / `"complete"` / `"finished"` — so a Qwen3 or DeepSeek-R1 thinking block mentioning *"I'm done analyzing area 1"* or *"the query completed"* ended the run. The parser is now strict: it walks every balanced JSON object (string-literal-aware, so `}` inside SQL strings no longer breaks the count), prefers the last block with a known action key (reasoning preambles no longer hijack the parse), and rejects anything without one. Unparseable responses are re-prompted up to three times with a reformat nudge instead of silently terminating. A new `MinSteps` exploration option (surfaced as `--min-steps` on the agent binary) rejects premature `done` signals, injects a nudge with the current/required step count, and continues — guarding against models biased toward early termination even with valid JSON. Covered by 40+ new unit tests including a Qwen3-style regression reproducing the original failure.

- **Ollama output tokens cap too low on large modern models** — The Ollama provider previously set a single `MaxOutputTokens["_default"] = 8192` for every model, which truncated long analyses on large reasoning and 2025/2026-generation models. Raised the default floor to 16384 and added documented per-model caps for the biggest Qwen, Gemma, DeepSeek, and Meta (Llama) families actually available in the Ollama library: 65536 for Qwen 3.5 / 3.6 (`qwen3.6:35b-a3b` tops out at 81920 per the model card), 32768 for DeepSeek R1 reasoning variants and Qwen 3 (32B / 235B), 16384 for Qwen 2.5 72B, DeepSeek V3, and Gemma 3 27B, and 8192 for Llama 4 Scout / Maverick, Llama 3.x (including the `llama3.1:8b` tag we recommend in our quick-start docs), Llama 3, and Gemma 2 (2B / 9B / 27B). Bare model names (`qwen3`) and `:latest` aliases are both mapped, and every documented Ollama size tag in the capped families is listed explicitly so the exact-match `GetMaxOutputTokens` lookup never silently falls through to the higher default.

- **Docker Compose Quick Start: `decisionbox-agent` missing from API image** — The API container's default `RUNNER_MODE=subprocess` spawns the agent via `exec.Command("decisionbox-agent", ...)`, but `services/api/Dockerfile` only shipped the `decisionbox-api` binary. Starting a discovery failed with `exec: "decisionbox-agent": executable file not found in $PATH`. The API image now also builds and installs `decisionbox-agent` into `/usr/local/bin`, so `docker compose up -d` works end-to-end out of the box. Kubernetes deployments are unaffected — they use `RUNNER_MODE=kubernetes` and run the agent as a Job from its own image.

## [0.4.0] - 2026-04-14

### Added

- **Vector search stack** — Full semantic search and RAG-powered insight Q&A built on Qdrant. Includes 6 embedding providers (OpenAI, Vertex AI, Bedrock, Azure OpenAI, Voyage AI, Ollama), a Qdrant vector store provider with HNSW search, and an embedding-settings tab in the dashboard. Agent Phase 9 denormalizes insights and recommendations into standalone collections, generates embeddings, and upserts them into Qdrant. New API endpoints: `POST /search` (semantic search with filters), cross-project search, `POST /ask` (RAG-powered Ask Insights), multi-turn ask sessions, search history with 90-day TTL, and standalone insights/recommendations CRUD. Dashboard adds a Search page, an Ask Insights chat page with citations and session history, Spotlight search (Cmd+K), and a recommendation detail page. Infrastructure: Qdrant subchart in Helm (auto-compute URL, API key secret), setup wizard Step 6 (vector search config), and a `qdrant` service in `docker-compose.yml`.
- **Dynamic domain packs** — Domain packs are now stored in MongoDB instead of compiled Go code. Create, edit, import, and export packs from the dashboard without code changes. New CRUD endpoints at `/api/v1/domain-packs` with a portable JSON import/export format. Dashboard adds a Domain Packs management page with a markdown prompt editor. Built-in packs (gaming, ecommerce, social) are seeded from embedded JSON on first startup. Removed `DOMAIN_PACK_PATH` environment variable — packs no longer read from the filesystem. Agent no longer depends on domain pack code and reads prompts entirely from project configuration.
- **Webhook notifications** — Notify external systems when discoveries complete via Slack, generic HTTP, or email webhooks. Configurable per-project with templated payloads.
- **Anonymous usage telemetry** — Collects anonymous, privacy-respecting usage metrics (version, OS, provider types, event counts). Enabled by default, disable with `TELEMETRY_ENABLED=false` or `DO_NOT_TRACK=1`. No PII, no query content, no credentials. See [TELEMETRY.md](TELEMETRY.md) for full details.
- **Helm dashboard `extraEnv` / `extraEnvFrom`** — `decisionbox-dashboard` chart now supports `extraEnv` and `extraEnvFrom` values, bringing it to parity with the API chart. Enables overlays to inject env vars and secrets without modifying the chart. Chart version bumped `0.1.0 → 0.1.1`.

### Changed

- **`apiserver.Run()` now owns subcommand routing** — The `backfill-embeddings` subcommand is dispatched inside `apiserver.Run()` instead of from `services/api/main.go`. Custom API binaries that call `apiserver.Run()` automatically get all subcommands wired up, closing a gap where subcommands were unreachable from custom entry points.

### Fixed

- **Go dependency security upgrades** — Resolved 18 Dependabot alerts (1 critical, 2 high, 15 medium) across 10 Go modules: `google.golang.org/grpc` (authorization bypass), `github.com/go-jose/go-jose/v3` (JWE decryption panic), `golang.org/x/oauth2` (input validation), and the AWS SDK v2 `bedrockruntime` / `eventstream` / `s3` packages (EventStream DoS). Dashboard Dockerfile now runs `apk upgrade --no-cache` to pick up Alpine security patches on rebuild.
- **IP allowlist wiring on AWS and GCP** — `setup.sh` was creating IP restriction resources in Terraform but never passing them to Helm, leaving the ALB / GCE ingress open to `0.0.0.0/0`. AWS now uses the `alb.ingress.kubernetes.io/inbound-cidrs` annotation (keeping the controller's backend SG management intact), and GCP now creates a `BackendConfig` CRD and annotates the dashboard Service with `cloud.google.com/backend-config` to attach the Cloud Armor policy.
- **Orphaned AWS `ip_allowlist` security group removed** — `aws_security_group.ip_allowlist` and its three supporting rules were no longer attached to anything after the switch to `inbound-cidrs`. Removed from the `terraform/aws` module along with the proxied output.
- **Terraform LLM IAM now granted to the API role, not just the agent** — `enable_bedrock_iam` / `enable_vertex_ai_iam` on AWS and GCP now also attach to the API's IRSA / Workload Identity SA. Previously the `/ask` endpoint (and any future API-side LLM call) returned 500 on EKS/GKE deployments with LLM IAM enabled because the API role had no `bedrock:*` or `aiplatform.user` permissions.
- **K8s test connection response parsing** — `extractJSONObject` now scans pod logs from the end and skips structured log lines (identified by the `"severity"` key). K8s pods mix stdout (result) with stderr (log lines), so the previous implementation picked up the first JSON line — a structured log, not the agent result — and the dashboard showed "Unknown error". Also adds `pods/log` to the `agent-job-manager` RBAC Role so the API can read agent pod logs.
- **Redshift SQL fix prompt** — The Redshift warehouse provider now returns a Redshift-specific self-healing prompt from `SQLFixPrompt()` (previously returned an empty string, so the agent's self-heal loop had no guidance for Redshift failures). Prompt covers the PostgreSQL features Redshift does not support (`DISTINCT ON`, `FILTER (WHERE ...)`, `LATERAL`, `generate_series`, `string_agg`, `array_agg`, `regexp_matches`, `FORMAT`), Redshift-native alternatives (`QUALIFY`, `LISTAGG`, `SUPER` + `json_extract_path_text`, `DATEADD`/`DATEDIFF`/`GETDATE`, `CONVERT_TIMEZONE`), and 17 common Redshift error patterns. `make lint-go` now includes the Redshift provider and CI has a matching `Lint Redshift warehouse provider` step.

### Removed

- Removed all Go code from `domain-packs/*/go/` directories (dynamic domain packs).
- Removed `libs/go-common/domainpack` package (registry, interfaces).
- Removed domain pack blank imports from agent and API server.

## [0.3.0] - 2026-04-06

### Added

- **PostgreSQL warehouse provider** — Connect to PostgreSQL databases with username/password or connection string authentication. Supports all common PostgreSQL data types including INTEGER, BIGINT, SERIAL, NUMERIC/DECIMAL (converted to float64), BOOLEAN, DATE, TIMESTAMP/TIMESTAMPTZ, BYTEA, JSON/JSONB, arrays, UUID, INET, and INTERVAL. Uses `information_schema` for table/column metadata and `pg_class.reltuples` for fast row count estimates. Includes comprehensive SQL fix prompt covering 13 error patterns (LATERAL joins, FILTER clause, recursive CTEs, NOT IN NULL trap, BETWEEN timestamp pitfall, and more). SSL mode configurable (default: `require`).
- **Databricks warehouse provider** — Connect to Databricks SQL warehouses via Unity Catalog with Personal Access Token or OAuth M2M (service principal) authentication. Uses the official `databricks-sql-go` driver with `NewConnector` structured options. Supports all Databricks data types including TINYINT through BIGINT, FLOAT/DOUBLE, DECIMAL (converted to float64), BOOLEAN, DATE, TIMESTAMP/TIMESTAMP_NTZ, BINARY, and complex types (STRUCT, ARRAY, MAP, VARIANT). Schema discovery via `catalog.information_schema`. Includes Databricks-specific SQL fix prompt covering QUALIFY, PIVOT/UNPIVOT, explode/explode_outer, Delta time travel, STRUCT/ARRAY/MAP access, and the `yyyy` vs `YYYY` date format pitfall.
- **Ecommerce domain pack** — Multi-category store analysis with 5 areas: conversion funnel, revenue & pricing, customer retention, product & category performance, and session & browsing behavior. Includes profile schema for store info, business model, fulfillment, marketing, and KPIs.
- **System-test domain pack** — Diagnostic domain pack for validating warehouse connectivity, schema discovery, data type mapping, and SQL dialect support. Not an industry pack — designed for testing and onboarding. Three categories by depth: quick (~10 queries), standard (~30-50 queries), thorough (~80-100 queries). Env-gated: only available when `DECISIONBOX_ENABLE_SYSTEM_TEST=true`.
- **Plugin middleware hooks** — Warehouse middleware (`warehouse.RegisterMiddleware()`) allows wrapping warehouse providers with custom logic such as logging, metrics, or access controls. HTTP middleware (`apiserver.RegisterGlobalMiddleware()`) allows wrapping all API requests. Agent startup logic exported as `agentserver.Run()` for custom builds. Context helpers `warehouse.WithProjectID()` / `ProjectIDFromContext()` for project-aware middleware.
- **Per-model max output token limits** — LLM provider metadata now includes `MaxOutputTokens` (model name → max output tokens). The agent's recommendation generation phase uses `gollm.GetMaxOutputTokens()` to request the model's full output capacity instead of a fixed 8K token limit. Lookup falls back to `_default` key, then to 8192.
- **Optional IP restriction for Terraform modules** — GKE, EKS, and AKS control plane access can be restricted to specific CIDR ranges via `allowed_cidr_blocks`. Setup wizard prompts for IP restriction and auto-detects the user's public IP.

### Fixed

- **Insight validation SQL fix parsing** — Fixed SQL fix prompt parsing that could fail when the LLM response contained extra formatting. Added missing schema context to validation queries, improving SQL fix success rate.

- **Snowflake warehouse provider** — Connect to Snowflake data warehouses with username/password or key pair (JWT) authentication. - **Azure Key Vault secret provider** — Store per-project secrets in Azure Key Vault with DefaultAzureCredential authentication (managed identity, Azure CLI, environment variables). Secret naming uses `{namespace}-{projectID}-{key}` format with managed-by tags for filtering.
- **Azure Terraform module** — Provision AKS, VNet, NAT Gateway, Managed Identities, and Key Vault on Azure. Follows the same module pattern as GCP and AWS. Includes Workload Identity federation, Container Insights, and deployment documentation.
- **Setup wizard Azure support** — The interactive setup wizard (`terraform/setup.sh`) now supports Azure as a third cloud provider. Handles `az login` authentication, Azure Blob Storage state backend, AKS credential configuration, Workload Identity annotations, and Key Vault integration.
- **Helm chart Azure Workload Identity** — Added `podLabels` support to API deployment template for `azure.workload.identity/use` label. Updated service account annotation examples for all three cloud providers (GCP, AWS, Azure).

- **Credentials moved to contextual tabs** — Warehouse credentials and LLM API keys are now managed inline in their respective settings tabs (Data Warehouse, AI Provider). The standalone Secrets tab has been removed.
